# Техническая архитектура PROBA

## 1. Статус текущего проекта

Репозиторий содержит интерактивный frontend-прототип на React и TypeScript. Данные хранятся только в состоянии интерфейса и сбрасываются после обновления страницы. Это позволяет проверять продуктовые сценарии без обработки реальных медицинских данных.

## 2. Предлагаемая архитектура MVP

```text
Telegram Bot ─┐
              ├── API Gateway / Backend
Telegram Mini App ┘        │
                           ├── Identity и Telegram initData
                           ├── Циклы, заказы и платежи
                           ├── Курьерские задания
                           ├── Каталог и цены лабораторий
                           ├── Результаты и согласия
                           ├── Врачи и консультации
                           └── Витрина и рекомендации
                                      │
                ┌─────────────────────┼──────────────────────┐
                │                     │                      │
         PostgreSQL             Очередь задач         Object Storage
                │                     │                      │
                └───────── адаптеры лабораторий и партнёров ─┘
```

Для MVP предпочтителен модульный монолит: один backend с чёткими внутренними модулями и одной транзакционной базой. Делить систему на микросервисы до появления реальной нагрузки и независимых команд не нужно.

## 3. Рекомендуемый стек

- frontend: React, TypeScript, Telegram Web Apps SDK;
- backend: FastAPI или NestJS;
- база данных: PostgreSQL;
- фоновые задачи: Redis + Celery/BullMQ;
- файлы: S3-совместимое хранилище с серверным шифрованием;
- платежи: провайдер с поддержкой чеков, возвратов и webhook;
- наблюдаемость: централизованные логи, метрики, error tracking;
- секреты: переменные окружения или отдельное хранилище секретов, никогда не Git.

## 4. Роли и доступ

| Роль | Доступ |
| --- | --- |
| `client` | Только собственные циклы, оплаты, результаты и согласия |
| `lab_operator` | Назначенные лаборатории заявки без лишних персональных данных |
| `doctor` | Только результаты, открытые действующим согласием клиента |
| `support` | Статусы и коммуникации, без медицинских значений по умолчанию |
| `admin` | Партнёры, аудит и инциденты; критические действия журналируются |

Для кабинетов партнёров нужна отдельная аутентификация с MFA. Telegram-аккаунт клиента нельзя использовать как единственный фактор для особо чувствительных операций вроде экспорта полной медицинской истории.

## 5. Основные сущности

| Сущность | Ключевые поля |
| --- | --- |
| `users` | Telegram ID, контакт, регион, настройки уведомлений |
| `kits` | код, партия, срок годности, статус, канал продажи |
| `cycles` | клиент, Kit, рекомендованный интервал, текущий статус |
| `test_catalog` | код исследования, название, единицы и требования к образцу |
| `lab_prices` | лаборатория, исследование, цена, срок действия |
| `orders` | состав, лаборатория, зафиксированная цена, платеж |
| `samples` | идентификатор, временные метки, температура, chain of custody |
| `courier_jobs` | слот, исполнитель, события доставки |
| `results` | показатель, значение, единица, референс, исходный файл |
| `consents` | субъект, врач, набор данных, срок, отзыв |
| `consultations` | врач, клиент, слот, статус, стоимость |
| `recommendations` | врач, основание, текст, срок контроля |
| `products` | продавец, категория, цена, юридический тип |
| `audit_log` | пользователь, действие, объект, время, IP и результат |

## 6. Жизненный цикл заказа

```text
draft
  -> priced
  -> payment_pending
  -> paid
  -> courier_scheduled
  -> sample_collected
  -> in_transit
  -> lab_received
  -> lab_accepted
  -> processing
  -> results_ready
  -> published
```

Отдельные конечные состояния: `cancelled`, `payment_failed`, `sample_rejected`, `refunded`, `incident_review`.

Переходы выполняются командами backend, а не произвольной записью статуса из клиента. Каждое внешнее событие должно быть идемпотентным.

## 7. Лабораторные интеграции

Для каждого партнёра создаётся адаптер с единым внутренним контрактом:

- получение каталога и прайса;
- отправка заявки;
- подтверждение или корректировка состава;
- статусы образца;
- получение структурированных результатов;
- получение подписанного исходного документа;
- отмена и фиксация ошибки.

При отсутствии API временным вариантом может быть защищённый кабинет лаборатории с ручным вводом или импортом утверждённого CSV. PDF без структурированных данных не должен становиться единственным источником динамики.

## 8. Безопасность

- проверять подпись Telegram `initData` на backend;
- не принимать Telegram user ID из тела запроса как доказательство личности;
- шифровать медицинские данные и резервные копии;
- отделить медицинские события от рекламной аналитики;
- выдавать короткоживущие ссылки на документы;
- журналировать просмотр результатов врачом и оператором;
- применять минимально необходимые права;
- иметь процедуры отзыва согласия, экспорта и удаления данных;
- не писать результаты анализов, токены и платежные данные в обычные логи.

До обработки реальных данных необходимы модель угроз, юридическая схема операторов данных, регламенты хранения и независимый аудит безопасности.
